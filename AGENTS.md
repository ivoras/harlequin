# Harlequin — Agent Guide

Client-server AI agent system in Go. A REST + WebSocket **server** talks to LLMs, stores data in SQLite, runs an agentic tool-calling loop, and manages skills; a Bubble Tea **TUI client** and a Svelte **web UI** talk to it. Multi-user, per-organisation.

## Binaries
- `cmd/harlequin-server` — REST + WebSocket API, LLM access, SQLite, agent loop, skills.
- `cmd/harlequin` — TUI client (Claude Code-like; dark-purple/light-green theme).
- `web/` — browser SPA (Svelte 5 + Vite; not a Go binary), one build with two pages over a shared core: the **desktop** UI at `/` (`web/index.html` → `src/desktop/`: sidebar + chat + right inspector, command palette, drag-and-drop uploads, light/dark theme) and the **mobile** UI at `/m/` (`web/m/index.html` → `src/App.svelte` + `src/views/`). Shared state and behaviour live in `src/lib/` (API client, session/WebSocket controller, composer, workspace boot, docs viewer state); desktop reuses several mobile `views/` (Memory, Skills, Cron, Hats, MCP, Config, Usage, Context, Login) and its `desktop.css` defines the same utility classes they rely on. The server's SPA fallback routes `/m/*` to `m/index.html`. `make web-build` → `web/dist`, served by the server when `server.web.dir` is set. Run `make web-build` after editing `web/`. User-facing features go in **all** clients (TUI + desktop web + mobile web).

## Stack
- Go 1.25. Router `go-chi/chi/v5`; Agent session streams, and chat are over WebSocket (`coder/websocket`).
- SQLite via `mattn/go-sqlite3` (CGO, `-tags sqlite_fts5`) + `asg017/sqlite-vec` (`vec0`). Build: `CGO_ENABLED=1 go build -tags sqlite_fts5 ./...` (or `make build`). Compile-time headers are vendored in `third_party/sqlite/`; no system `libsqlite3-dev` needed.
- TUI: `charm.land/{bubbletea,bubbles,lipgloss}/v2`, `glamour` + `chroma` for rendering.
- JS engine: `dop251/goja` (ES5.1-compatible, much of ES6 incl. let/const, classes, Promise, BigInt; sandboxed) for `<?js ?>` skill templating and the `run_js` tool.
- Config: YAML (structure) + `.env` (secrets); env overrides YAML. Models are defined only in `model_suites` (selected by `model_suite`); per-model `price`, `context_window`, `local`, `fallback_model` sit next to the model, and `config.resolveModelSuite` expands them into providers/routing/prices/embeddings. Top-level `providers`/`routing`/`embeddings` are rejected at load.

## Layout
- `internal/server/{config,db,storage,auth,api,llm,embed,jsrun,agent,memory,documents,conversation,dom,sandboxfs,pdfextract,mdtmpl,audit,sessionlog,usage,session,sessionhub,presence,project,projectchat,skills,userconfig,cron,mcp,webfetch,email,notify,notifyx,telegram,secrets}` — `session` is the chat-session store (the `sessions` table + messages); `sessionhub` is the live-session runtime (one goroutine per active session; see Live sessions below); `project` is the project registry + chatroom store and `projectchat` the chatroom broadcast hub (see Projects below); `notify` is the notification store and `notifyx` the delivery dispatcher (in-app / email / Telegram).
- `internal/server/skills/jstmpl` — PHP-style `<?js ?>` templating (on `jsrun`).
- `internal/client/{config,apiclient,tui,skills}`
- `internal/shared/types` — REST DTOs. `internal/server/db/migrations/{system,shared,user,project}/*.sql` and `skills/` embedded via `embed.FS`.

## Concepts
- Layered memory + documents: user + shared (organization-level) + projects
- Skills are a set of virtual documents: the main skill file, referenced as "skill://name", and optional files such as scripts, referenced e.g. as "skill://name/file/name.md"
- All search (docs, memory, skills) fuses project scope (if active), then shared scope, then user scope
- A **hat** is a working mode: a role description plus (optionally) specialised skills that **overlay and take precedence over** whatever the project/shared/user scopes would resolve. While a hat is worn, its skill copies (files under `skills/<name>/...` in the hat) win outright, and its optional frontmatter `skills:` list restricts which skills are visible. The point is that certain people need their specialised skill variants for certain kinds of tasks, without touching the originals. The hat's `system_prompt.md` body is **added to** the default system prompt; frontmatter `replace_prompt: true` replaces it instead (`use_prompt: false` switches the body off). A user wears at most one hat per session; hats and projects are independent of each other. See the Hats section below.

## Usage accounting
- Every paid model call is a `usage` row (user db; `usage_unattributed` in the system db when no user is known), costed from the provider's reported `cost` (`cost_reported = 1`) or else the price table. This covers **chat/aux/vision completions and embeddings** (`provider = "embed"`, prompt tokens only): `embed.OpenAIEmbedder.SetUsageFunc` feeds the same `recordUsage` recorder, using the response's `usage` (tokens, cost) or a chars/4 estimate when it has none. Attribution (`llm.Attribution`) rides on the context: agent turns set it, `attributeRequest` middleware defaults it to the authenticated caller, document ingest sets it to the uploader (+ project). New paid call paths must go through the recorder so the totals reconcile with the provider's billing.

## LLM cost markup
- `server.org_llm_markup_percent` (default 0; this deployment sets 5) is the organisation's margin on LLM cost. It is applied **only on the way out**: recorded `usage`/`usage_unattributed` rows and the server log keep the provider's figures. Every API response that carries a cost goes through `Server.markup` (`internal/server/api/markup.go`): `/usage`, `/usage/daily`, `/usage/users` (incl. the unattributed row), the session cost in `/sessions/{id}/context`, and `cost_usd` in the `/sessions/{id}/log` trajectory. A new endpoint or event that exposes a cost must do the same. Users are not told about the markup — keep it out of user-facing text and docs (the UI must not claim a figure is the provider's own).

## Hats
- **Prompt**: `agent.hatPrompt` = default prompt + `You are wearing the "<name>" hat.` + the hat body (unless `replace_prompt`) + a catalogue of the wearable hats (name + description; the agent may suggest one but never switches unasked). `contextusage` calls the same function so the numbers cannot drift.
- **Sticky**: the last worn hat is remembered per user (`hat.last` in the per-user config); a new session created without a hat starts with it if it still exists. Taking the hat off clears it. `agent.SetSessionHat` is the one place that changes a session's hat (REST `POST /sessions/{id}/hat`, `POST /projects/{id}/sessions/{sid}/hat`, and the `wear_hat` tool): it validates, writes the session (user or project db), updates `hat.last`, and publishes a `docevents.HatChanged` that every connected client of the session receives as a `hat_changed` frame (`StreamEvent.HatChange`).
- **Personal hats** can't be worn in a project session (the session is shared and other members can't read the wearer's `user.db`): `SetSessionHat` refuses (`skills.ErrPersonalHatInProject`), `loadHat` ignores one that got there anyway, and assigning a session to a project drops a personal hat. Cron jobs (personal sessions) can use them.
- **Cron**: skill-kind jobs have an optional `hat` (`cron_jobs.hat`); `cron_create` defaults it to the session's hat; a run whose hat no longer exists fails with an error.
- **Baked hats** (`hats/<name>/system_prompt.md`): `analyst`, `researcher`. They are role text only (no `skills:` list, no overlays).
- A session pointing at a hat that no longer exists reports no hat in session listings (`dropGoneHats`).

## Projects (shared workspaces)
- A **project** is a shared workspace grouping members, sessions, documents, and memories, plus a live chatroom. Registry (projects/members/invites) is in the **system** db (`migrations/system/0002_projects.sql`, `internal/server/project`). Only one project can be active. Any user can create a project (becoming the first member); any member can invite others (by email; the invitee gets a notification and accepts) and **assign** a session to the currently active project.
- **Assigning** a session *moves* it (and its messages) from the owner's `user.db` into the project db (`project.MoveSessionToProject`), so a session belongs to at most one project and every project member sees it. Project sessions are a **shared live session**: the sessionhub keys them by `p/<projectID>/<sessionID>` (vs `u/<userID>/…`), so all members attach to the same live turn; `agent.Run` takes a `projectID` and runs the turn on the project db (`rc.sessDB`) while user-scoped tools (skills/MCP/cron/usage) stay on the acting user's db. WS: `GET /projects/{id}/sessions/{sid}/ws`.
- **Project memory** uses composite-id scope `p.<localid>` in the project db; a project session fuses user+shared+project (`memory.SearchFused`) and `memory_write`/auto-extraction (from a chat turn: `memextract.TurnPrompt`, which in a project session files personal facts to the user's memory and the project's matters to project memory; from an uploaded document: `Agent.ExtractMemoriesFromDoc`, at most `memextract.MaxDocumentMemories` lasting facts stored in the document's own scope with `memories.source_doc` pointing at it — never chosen by the model; `harlequin-server rederive-doc-memories` re-runs it over existing documents) default to the project scope (any member may write it).
- **Chatroom**: `internal/server/projectchat` (broadcast hub, no turn buffer), communication over the websocket; messages persist in the project db (`chat_messages`). Clients show a side-pane only while a project is active (web right-hand pane / TUI split; `/project` to manage, `/say` in the TUI to post). Hats stay orthogonal to projects.
- **Documents are scoped like memory** (personal/shared/project). Each corpus lives in its tier's db (`user.db` personal, `shared.db` org, `project.db` project) with its own `documents`/`doc_chunks`/`doc_chunks_fts`/`doc_chunks_vec`. `documents.SearchScoped`/`ScopesFor(userDB, projDB)` fuse the corpora with the same RRF as a single store — a project session adds the project corpus (`rc.projectDB` is set only then), otherwise personal+shared — and every hit is **scope-labelled** (`SearchResult.Scope` ∈ personal/shared/project; chunk ids are `d.{u,s,p}.<n>`). `search_docs` (agent), `GET /documents/search` (`?project=<id>` to include a project), and the skill `SearchDocs` helper all fuse; ingest picks the target corpus via `CreateDocumentRequest.Scope` (`personal` default, `shared` for owners/admins, or `project`+`project_id` for members; `save_doc` defaults to the project in a project session). Scope rules are documented for users in `docs/SCOPES.md` (projects: `docs/PROJECTS.md`, roles: `docs/USERS.md`).

## Storage
- `internal/server/storage.Manager` owns the handles. `data/harlequin.db` (system: contains users, api_tokens) and `data/shared.db` (org: shared memories, documents, org-scope skills incl. the seeded baked-ins) are **kept open**. 
- Each user has `data/users/<id>/user.db` (their memories, sessions, messages, usage, audit, user-scope skills, cron jobs, and a generic `config` key/value table), **opened and closed per request** via `WithUser`; `EachUser` fans out for admin aggregation and maintenance sweeps. Uploaded files go to `data/shared_files/` and `data/users/<id>/files/`.
- Each project's own data lives in `data/projects/<id>/project.db` (`db.Project` role; `storage.WithProject`/`EachProject`), holding project-scope memories, docs, skills, mirroring the per-user lifecycle. 
- Hats live in two scopes: **shared** in `shared.db` (`hats`/`hat_files`; per-hat skill overrides are `hat_files` rows under `skills/<skill>/...`) and **personal** in the user's `user.db` (same tables, `migrations/user/0014_hats.sql`, no seed table). Baked-in hats are seeded like skills (and removed from the DB again when dropped from the binary, if untouched); any legacy `<data_dir>/hats/` directory is imported once at startup. A shared hat shadows a personal one of the same name (creating a clashing personal hat is refused). Every user can wear shared hats and their own; shared hats are edited by owners/admins, personal hats by their owner (`PUT|DELETE /hats/{name}` pick the scope from where the hat lives; `POST /hats` takes `scope`, default personal).
- No cross-file foreign keys: memory ids are composite strings `u.<localid>`/`s.<localid>`/`p.<localid>`, and `memory_conflicts` endpoints/ids are composite (conflicts involving a user memory live in that user's db; shared–shared in `shared.db`).

## Core flows
- **Auth**: email/password login -> issued API bearer token (SHA-256 in DB); middleware injects user/role. Email is the identity (`users.email`). Self-registration (`/auth/register` -> emailed 6-digit magic code -> `/auth/verify`) holds signups in `pending_registrations` until verified; gated by `auth.allow_registration` (default true). Codes go through `internal/server/email` (SMTP, or logged to console when `smtp_host` is empty).
- **Roles** (`types.IsOwner`/`types.IsElevated`): `owner` > `admin` > `user`. Owner is the only role that can create/edit users (`requireOwner`). Owner+admin ("elevated", `requireElevated`) may create/delete shared memories, delete documents, read the audit log, publish skills, and view other users' usage. Ordinary users get their own sessions and user-scoped memories only — the `memory_write` tool refuses `shared` scope for them.
- **Chat**: client connects the session WebSocket (`GET /sessions/{id}/ws`) and submits a prompt frame -> agent loop composes prompt with resolved skills, calls the LLM provider (routing + fallback), dispatches tool calls (`memory_search`, `memory_write`, `memory_change`, `memory_delete`, `memory_feedback`, `ask_user`, `notify_channels`, `calculator`, `list_skills`, `load_skill`, `run_js`, `search_docs`, `save_doc` (inline `content` or a sandbox `source`), `edit_doc` (replace/diff/append/append_source/insert-after-or-before-a-passage on a saved document, keeps its id, re-indexes incrementally; text documents are edited directly, documents made by `create_excel`/`create_pdf`/`create_word` via their `<stored>.src.json` source sidecar, which is regenerated; `undo` restores the `.prev` copy; uploaded Word `.docx` files are edited in place at paragraph level by `internal/server/docxedit` (replace/insert/append; XML spliced by byte range, other zip entries copied, output self-checked; text re-derived like an upload's), uploaded Excel `.xlsx` files likewise in place by `internal/server/xlsxedit` (excelize; `cells`/append/insert/replace, `sheet` arg; read_doc `cells: true` gives the sheet/address grid; output re-read and compared cell by cell), uploaded PDFs are refused), `edit_file` (same ops on `tmp://`/`storage://`; `append_source` concatenates whole documents/files server-side), `copy_doc` (document or sandbox file → sandbox file or new document), `create_excel`, `create_pdf` (Markdown or sanitised HTML → PDF via sandboxed headless Chrome, `internal/server/mdpdf`), `create_word` (same sources → DOCX via sandboxed headless LibreOffice, `internal/server/mdword`), `pdf_pages` (copy pages of existing PDFs into new ones: extract/split/merge, many outputs per call; `pdfextract.Assemble`), `check_text` (one phrase, or `texts` = many phrases → pages in one call), `send_email` (Markdown body, optional `attachments`), `wear_hat` (only when the user asks), `create_project`/`move_doc` (owner/admin only; move_doc copies a document into a project the user belongs to, optionally deleting the original), `Grep`, `cron_create`/`cron_list`/`cron_update`/`cron_run`/`cron_delete`, `WebFetch`, `WebFetchDOM`, `WebFetchGrep`, `MarkdownFetch` (URL → Docling → Markdown, content not summary; only when a `documents.docling`/`xberg` converter is configured), skill-defined tools, MCP tools; reference in `docs/TOOLS.md`; document tools take a sandbox path (`tmp://`, `storage://`, bare = `tmp://`) wherever a document id fits — `isSandboxPath`/`sourceText` in `agent/doccopy.go`), loops to `max_steps`, streams event frames. A streaming LLM call is cancelled and retried once (then errors) when `llm/loopdetect` sees its reasoning/content repeating verbatim, or reasoning exceeds `maxThinkingChars`; the partial output is logged (`llm_response` with `partial`, `reasoning_loop`). **Provider outages**: `llm.RoutingProvider` retries transient failures (network, 408/429/5xx; `llm.IsTransient`) with backoff, then tries the next provider, then the chat model's `fallback_model` (model suite; skipped if the prompt would not fit its `fallback_context_window`; the primary is then treated as down for 30s). A stream that dies mid-answer re-runs that step (2 retries, then one on the fallback model; `llm_retry` log event). A failed turn's error is stored as a `role: "error"` message (shown by all clients, never sent to the model). `memory_write`/`memory_change` surface detected conflicts in their result so the model can warn the user; `ask_user` emits an `ask_user` event and ends the turn so the user can reply.
- **Live sessions** (`internal/server/sessionhub`): each active session is a server-side goroutine that runs turns under a *session-scoped* context (over WebSocket), so a client disconnect does not cancel the turn. It buffers the in-flight turn's events with a session-monotonic `Seq` and fans them out to all connected WebSocket subscribers; the goroutine exits after `sessions.idle_timeout` (default 30m) with no connection and no running turn. **Resume**: a (re)connecting client sends `hello{have_seq}`; the server replies `synced{running, committed_through, seq}` then replays buffered events with `seq > have_seq` and continues live. Cold resume (have_seq 0): the client loads committed messages via `GET /sessions/{id}/messages`, renders those with `id <= committed_through`, and reconstructs the in-flight turn from the replayed buffer (which re-emits it from a `user_message` echo). WebSocket auth accepts the bearer token from the Authorization header (Go clients) or the `bearer.<token>` subprotocol (browsers). The Web UI keeps the session id in `?c=<id>` so a refresh resumes; the TUI resumes via `/resume` (a session picker), `/resume <id>`, or the `--session <id>` launch flag.
- **Notifications** are **pushed** over the session WebSocket, not polled: each connection runs a server-side poller (`Server.pollNotifications`, ~5s) that reads the user's pending notifications (the DB is the store, `notify.ListPending` filtered by interface) and sends new ones as `notification` events; clients ack over REST (`POST /notifications/{id}/ack`). Clients render passive notifications in a **persistent alert box** above the transcript (not in the session transcript), kept until dismissed (web ✕/Run buttons; TUI `/dismiss [n|all]` and `/run <n>`); session-title updates and auto-run prompts are handled as control/behaviour, not shown as alerts. The same notifications are the intended payload for future delivery to other interfaces (e.g. Telegram).
- **Document change pushes**: `internal/server/docevents` is an in-process bus. Document create (API ingest/upload, `save_doc`), update (`edit_doc`) and delete (API, `delete_doc`) publish an event; each session WebSocket subscribes (own personal docs, shared docs, project docs of projects the user belongs to) and sends a connection-level `documents_changed` frame (`StreamEvent.Doc`, not in the replay buffer). Web clients answer by re-listing (`bumpDocs`/`docsVersion` in `web/src/lib/stores.ts`, debounced); the TUI has no live document list and ignores it. New code paths that create/modify/delete documents must publish.
- **Document editing** (`edit_doc`, `agent/editfile.go`): what to do is decided by where the document came from. A `<stored file>.src.json` sidecar (written by `create_excel`/`create_pdf`/`create_word`: kind, format, landscape, source text) → edit the source and regenerate the file via the shared `generate`; a `text/*` original → edit the text; an uploaded `.docx`/`.xlsx` (no sidecar) → edited inside the original file by `docxedit`/`xlsxedit`, which self-check the output before returning it; an uploaded PDF is refused. Every path ends in `commitDocEdit` (stage files, incremental `ReplaceContent`, `.prev` copy for the one-step `undo`); new document kinds plug into the dispatch there, and any new code that writes a stored file must keep the sidecar and `.prev` files with it (`DeleteFrom`/`CopyInto` already do).
- **Skills**: live in the scoped databases; resolution precedence **project -> shared -> user** (deeper scope wins, same order as docs/memory). Baked-in skills **and hats** are embedded in the binary and **seeded into `shared.db`** on startup (`skills.Seed`, hash-guarded via the `*_seed_hashes` tables: human edits in the DB are preserved). Top-level baked files (e.g. `skills/system_prompt.md`) are not skills and are read straight from the binary. Server is the single source of truth; clients pull/push via `/skill` slash-commands. Skills support inline `<?js ?>` and frontmatter-declared tools.
- **WebFetch** (`internal/server/webfetch`, on by default, `agent.web_fetch.enabled: false` to disable): fetches a URL with browser-like anti-bot measures — realistic Chrome headers, a uTLS Chrome JA3/TLS fingerprint, HTTP/2, a cookie jar, redirect following, request jitter (no headless browser, no CAPTCHA solving) — converts HTML to Markdown (`JohannesKaufmann/html-to-markdown`), then analyses it with a small model (`agent.web_fetch.model`) given only the WebFetch tool. http→https upgrade; 15-minute per-URL cache; SSRF guard blocks private/loopback targets unless `allow_private`. **Zyte fallback** (when `ZYTE_API_KEY` is set): a direct fetch that returns HTTP 4xx is retried through Zyte's `browserHtml` API, and the URL's domain is remembered in a thread-safe in-memory set so later fetches of that domain skip straight to Zyte (`via_zyte` in the log). The fallback lives in `webfetch.Client.FetchRaw`, so it covers every agent-initiated fetch alike — the WebFetch tool, the sandbox `fetch()` used by JS cron jobs, and the web-monitor skill (one shared `Client`). The trajectory logs each fetch (`web_fetch`: url, final_url, cached, fetch_ms, bytes) and the delegated inner LLM call (`delegated_llm_request`/`delegated_llm_response`, labeled `delegate: web_fetch`, with `duration_ms`). Companion tools on the same fetch pipeline: **WebFetchDOM** (sandboxed JS over the parsed DOM, `internal/server/dom` + `sandboxfs`) and **WebFetchGrep** (deterministic regex over the fetched HTML; an optional prompt runs the analysis model over the matches).
- **Session logging**: full chat trajectory written as JSONL at `<data_dir>/sessions/<user_id>.<conv_id>.jsonl` (ids zero-padded to ≥5 digits). Optional via `sessions.enabled` (default true).
- **Interfaces**: each session is tied to one *interface* (the medium a user talks through) plus its *API* (transport), stored on the session (`api`, `interface` columns) and logged in `session_start`. REST clients announce the interface via the `X-Harlequin-Interface` header (TUI → API `REST` / interface `TUI`; the web SPA → `Web`); cron-started sessions use `Cron`/`Cron`; a planned Telegram chat bridge sets `Telegram`/`Telegram` (today Telegram is outbound-only: `notifyx` delivers notifications via `internal/server/telegram`). Add an interface by announcing a new header value, or set api/interface directly in a server-side bridge. Constants in `internal/shared/types` (`InterfaceTUI`, `APIREST`, …).
- **Per-user config**: generic key/value `config` table in `user.db`, via `internal/server/userconfig.Store` (Get/Set/Delete/All) and REST `/config`, `PUT|DELETE /config/{key}` (TUI `/config`). Holds small settings that don't warrant their own table — e.g. registering a Telegram connection (`telegram.chat_id`, `telegram.username`).

## Conventions
- **"Simple things should be easy, complex things should be possible" — judged from the user's chair, not the code's.** A user doing the common thing (chatting, uploading a file, saving a report, remembering a fact) must succeed with zero flags, zero scope decisions, zero reading — the defaults carry them. A user doing the rare thing (org-wide document, cross-project search, a specific project's citation, a hat overlay) must have a working path to it, even if a longer one. Internal complexity is fine and often the price of that surface: we absorb complexity in the software so users don't pay it in the interface. What's forbidden is the inverse — simplifying the implementation by making users choose, configure, or know things they shouldn't have to.
- **Principle of least astonishment (POLA) governs every user-facing decision** — features, defaults, tool behavior, references, errors. Harlequin is a multi-user assistant whose users can't read the code: whatever a reasonable user would predict (from names, conventions, or what a sibling feature does) is the spec. Concretely: safe defaults (personal scope, not shared), symmetric capabilities (anything visible on the read side must be writable/openable where the user would expect), references that mean the same thing everywhere they appear, and failures that are loud and persistent rather than silent or transient.
- **Naming of scopes: "personal", "shared", "project".** Everything a user reads — UI labels, pills, dropdowns, slash-command output, flags, docs, error messages — says **personal** for the single-user tier (never "user"/"user scope": "user" already means the account and the `user` role) and **shared** for the organisation-wide tier ("organisation" only in descriptive prose). The API keeps `user` as the wire value for skills, memories and MCP servers (`personal` for documents and hats) — don't rename stored/API values; translate at the display edge (`scopeLabel` in `web/src/lib/scope.ts`, `displayScope` in `internal/client/tui`). Commands that take a scope accept `personal` and keep `user` as a silent alias (`/skill … --personal|--user`, `/memory personal|user`, `/mcp personal/…`). New scope-aware UI follows this.
- Comments should be terse and explain the non-obvious (the *why*, edge cases, gotchas); don't restate what the code plainly says.
- Secrets only in `.env`, never in YAML or code.
- URLs built with names in the path (skill name, hat name, file relpaths, config keys, …) must URL-encode those strings: Go `url.PathEscape` per segment (`apiclient.escapePathSegments` for relpaths), web `encodeURIComponent` (the `q()` helper in `web/src/lib/api.ts`).
- `docs/user_guide.md` is the user-facing documentation. Its "Slash commands in the TUI" chapter must be kept in sync: whenever a TUI slash command is added, removed, or changes syntax (`internal/client/tui/slash.go`, `helpText` in `commands.go`), update that chapter in the same change.
- All JS (templating, `run_js`, skill tools) runs through the sandboxed `jsrun` runner: no file/network (except allow-listed `fetch`), hard `vm.Interrupt` timeout, output cap.
- **Autonomous LLM judgments**: any server process that is *not* directly started by the user (background workers, post-turn hooks, scheduled jobs, etc.) and asks the LLM to *judge* whether to take an action must:
  1. **Request a confidence score** — instruct the model to attach an integer `confidence` field (1–10) to every judgment, meaning how sure it is the result is correct and safe to act on without user confirmation.
  2. **Gate on the score** — only accept and act on judgments with `confidence >= 7`. Discard or ignore everything below the threshold.
  3. **Prefer structured output** — use JSON (or an equally machine-parseable format), not free-form prose lines.
  4. **Silence on uncertainty** — if nothing meets the bar, return an empty collection or explicit negative; never persist placeholder/meta text (e.g. "no facts found").
  - Shared helpers live in `internal/server/llm/judge` (`MinConfidence`, `Accept`, `Clamp`, `PromptRules`, `ParseJSONObject`). Domain-specific parsers (e.g. `internal/server/agent/memextract`) embed `judge.PromptRules()` and call `judge.Accept` before side effects.
- **No client data in the repository.** Never put real client names, their people, companies, documents, figures or any other client-specific information into code, tests, fixtures, documentation, config examples or commit messages (or PR descriptions). Use neutral placeholders (e.g. "Acme d.o.o.", "Ana Horvat"). This applies to examples taken from real sessions or uploads too: anonymise them first.
